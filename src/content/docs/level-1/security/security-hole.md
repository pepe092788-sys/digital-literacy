インターネット上では、さまざまな不正アクセスや情報漏洩事件が発生しています。

ハッキングという言葉を聞くと、高度な技術を持った攻撃者が、コンピュータの防御を強引に突破するようなイメージを持つかもしれません。

しかし、攻撃の多くは、システムがもともと持っている機能や、その機能に存在する弱点を悪用することで成立しています。

では、システムのどのような場所に弱点が生まれるのでしょうか。

攻撃手法の名称ではなく、攻撃が成立する原因に注目してみましょう。

## セキュリティホールとは

セキュリティホールとは、第三者による不正な操作や情報の取得などを許してしまう可能性のある、システムのセキュリティ上の弱点です。

一般的には「脆弱性（ぜいじゃくせい）」とも呼ばれます。

プログラムの記述ミスだけでなく、設計上の問題や設定の不備、アクセス権限の管理不足などによっても生じます。

例えば、会員制のWebサイトで、自分の個人情報を確認できる機能があるとします。

本来は自分の情報だけを閲覧できるはずですが、システムの不備によって、他人の個人情報まで閲覧できてしまうとしたらどうでしょうか。

画面は正常に表示され、プログラムも動作しています。

それでも、安全なシステムとはいえません。

**プログラムが正常に動作することと、許可された操作だけが行われることは別の話なのです。**

## システムが異なっても、狙われる場所には共通点がある

ショッピングサイト、業務システム、SNSなど、世の中にはさまざまな情報システムがあります。

目的や機能は異なりますが、多くのシステムには共通する仕組みがあります。

利用者を確認する。外部から情報を受け取る。データを保存する。別のシステムと通信する。

こうした仕組みの周辺には、セキュリティ上の弱点が生まれる可能性があります。

| 狙われる場所 | 本来の役割 | 弱点が生まれる原因 |
| --- | --- | --- |
| ログイン機能 | 利用者を確認する | 本人確認が不十分 |
| 入力フォーム | 外部から情報を受け取る | 入力内容を安全に扱っていない |
| アクセス権限 | 操作できる範囲を制限する | 権限の確認が不十分 |
| データの保存場所 | 必要な情報を保管する | 秘密情報の管理が不適切 |
| 管理機能 | システムを管理する | 不要な機能の公開やアクセス制限の不備 |
| 通信機能 | 情報を送受信する | 通信相手や内容の保護が不十分 |
| 外部ソフトウェア | 既存の機能を利用する | 脆弱性や不正な変更への対策が不十分 |
| 処理能力 | 利用者の要求を処理する | 想定外の負荷への備えが不十分 |

これらの場所に機能があるだけで、セキュリティホールになるわけではありません。

その機能を安全に利用するための仕組みに欠陥があることが問題なのです。

それぞれの場所について、もう少し詳しく考えてみましょう。

## ① ログイン機能 ― 本当に本人なのか

ログイン機能は、利用者が誰であるかを確認するために存在します。

例えば、パスワード認証では、正しいパスワードを知っていることを本人確認の手がかりとします。

しかし、パスワードが第三者に知られてしまった場合、システムは本人と第三者を区別できない可能性があります。

本人確認に使う情報が推測されやすかったり、盗まれた情報だけで認証を突破できたりすることが弱点になります。

多要素認証やパスキーは、こうした問題を減らすための技術です。

**考えるべきこと：何を根拠に、その利用者を本人だと判断しているのか。**

## ② 入力フォーム ― 受け取った情報をそのまま信頼していないか

Webサイトには、検索欄やお問い合わせフォームなど、利用者が情報を入力する機能があります。

システムは入力された情報を受け取り、必要な処理を行います。

例えば、商品検索では、入力された商品名を使ってデータベースから情報を取得します。

ここで、入力された文字列を単なる検索条件として扱うべきところ、プログラムの作り方によっては、データベースに対する命令として解釈されてしまう場合があります。

コンピュータが勝手に命令を作り出したわけではありません。データと命令を適切に分離できていないことが原因です。

この弱点を悪用する代表的な攻撃が、SQLインジェクションです。

入力された情報の形式や内容を確認するとともに、外部のデータがプログラムの命令として扱われない仕組みが必要になります。

**考えるべきこと：外部から受け取った情報は、どのような処理に使われるのか。**

## ③ アクセス権限 ― ログインできることと、何でもできることは違う

会社の業務システムでは、一般社員と管理者とで、操作できる機能や閲覧できる情報が異なることがあります。

本人確認ができたとしても、その人にすべての操作を許可してよいわけではありません。

| 確認すること | 役割 |
| --- | --- |
| 認証 | 利用者が誰であるかを確認する |
| 認可 | その利用者に操作を許可してよいかを確認する |

例えば、一般社員がログインできることと、他の社員の給与情報を閲覧できることは別の話です。

画面上で管理者用のボタンを非表示にするだけでは、十分なアクセス制限にはなりません。

実際に処理を行うシステム側でも、その操作が許可されているかを確認する必要があります。

**考えるべきこと：誰が、どの情報に対して、どのような操作を許可されているのか。**

## ④ データの保存場所 ― 秘密情報はどこに存在しているのか

情報システムでは、パスワードや個人情報など、第三者に知られてはいけない情報を扱います。

しかし、プログラムのソースコードにパスワードを直接書き込んでいたり、誰でも閲覧できる場所に機密情報を保存していたりすれば、その情報が流出する可能性があります。

また、保存されている情報を読み取れる人や、書き換えられる人の範囲が広すぎることも問題になります。

秘密情報を適切な場所に保管し、必要な人やプログラムだけが利用できるようにすることが重要です。

**考えるべきこと：守るべき情報はどこにあり、誰がアクセスできるのか。**

## ⑤ 管理機能 ― その機能を外部に公開する必要はあるのか

Webサイトには、記事の編集やユーザーの管理など、管理者だけが使う機能が存在する場合があります。

しかし、一般の閲覧者には記事を読む機能だけがあれば十分です。

管理機能を外部からアクセスできる状態にする場合は、不正な操作を防ぐ仕組みが必要になります。

そもそも外部に公開する必要がないのであれば、管理環境と公開環境を分離することもできます。

公開環境に必要のない機能を設置しなければ、その機能を直接狙う攻撃経路を減らすことができます。

**考えるべきこと：その機能は、本当に外部から利用できる必要があるのか。**

## ⑥ 通信機能 ― 本当に正しい相手と通信しているのか

情報システムでは、利用者の端末とサーバーの間や、異なるシステム同士で情報をやり取りします。

その通信が適切に保護されていなければ、情報を読み取られたり、書き換えられたりする可能性があります。

また、通信内容が暗号化されていたとしても、接続先そのものが偽物であれば、入力した情報は偽の接続先に届いてしまいます。

通信の安全性を考える際には、情報の保護だけでなく、通信相手を確認することも重要です。

**考えるべきこと：誰と通信しているのか、その情報は途中で読み取られたり改変されたりしないか。**

## ⑦ 外部ソフトウェア ― 他人が作った機能をどこまで信頼するのか

現代の情報システムは、すべての機能を一から開発しているわけではありません。

他の開発者が作成したライブラリやプラグイン、外部サービスなどを組み合わせて構築することも一般的です。

既存の機能を利用できることで、開発は効率的になります。

一方、そのソフトウェアに脆弱性が存在すれば、自分で開発した部分に問題がなくても、影響を受ける可能性があります。

信頼しているソフトウェアの提供元が侵害されることもあります。

こうしたリスクに備えるには、信頼できる提供元を選び、必要な更新を行い、不要なソフトウェアを増やさないことが重要です。

**考えるべきこと：自分のシステムは何に依存しており、それらは適切に管理されているのか。**

## ⑧ 処理能力 ― 想定外の使われ方にも対応できるのか

情報システムには、一度に処理できる情報量や利用者数に限界があります。

通常の利用では問題なく動作していても、処理能力を超える大量の要求を受けると、サービスを提供できなくなる場合があります。

この性質を悪用し、意図的にサービスを利用できなくする攻撃もあります。

代表的なものがDoS攻撃やDDoS攻撃です。

情報を盗まれることだけが、セキュリティ上の被害ではありません。

必要なときにシステムを利用できなくなることも、重大な問題です。

**考えるべきこと：通常とは異なる使われ方をしたときにも、必要な機能を維持できるのか。**

## 共通しているのは、信頼の境界

ここまで見てきた弱点には、共通する考え方があります。

それは、異なる立場や役割を持つものの間で、何を根拠に信頼するのかという問題です。

| 境界 | 確認すべきこと |
| --- | --- |
| 本人と第三者 | 本人であるか |
| 外部の情報と内部の処理 | 安全に処理できる情報か |
| 一般利用者と管理者 | 操作を許可してよいか |
| 公開情報と秘密情報 | 閲覧を許可してよいか |
| 正規の通信相手と第三者 | 信頼できる通信相手か |
| 自分のシステムと外部ソフトウェア | 安全に利用できるものか |

セキュリティ設計では、異なる信頼水準を持つ領域の境目を「信頼境界」と呼びます。

すべての脆弱性が信頼境界だけで説明できるわけではありませんが、多くの弱点を理解するための有効な視点です。

システムのどこで情報を受け取り、どこで権限を確認し、どこまで相手を信頼するのか。

こうしたことを考えると、個々の攻撃手法に共通する原因が見えてきます。

## 攻撃される場所と、セキュリティホールは異なる

ここで、二つの概念を区別しておきましょう。

| 概念 | 意味 |
| --- | --- |
| アタックサーフェス（攻撃対象領域） | 攻撃に利用され得る接点や経路 |
| セキュリティホール（脆弱性） | 攻撃などによって悪用され得る安全性の欠陥 |

ログイン機能は攻撃対象領域の一つですが、ログイン機能そのものが脆弱性というわけではありません。

本人確認の仕組みに不備があることが、脆弱性になります。

攻撃対象領域を減らすことと、残された機能の脆弱性を解消すること。

どちらも安全性を高めるために重要です。

## AI時代だからこそ、弱点が生まれる場所を知る

生成AIを利用することで、プログラミングの経験が少なくても、Webアプリや業務用のツールを作れるようになりました。

しかし、期待どおりに動作するプログラムが完成したからといって、安全性まで確認できたことにはなりません。

ソースコードをすべて理解できなくても、次のような視点を持つことには意味があります。

- 外部から受け取った情報は安全に処理されるか。
- 本人確認や操作権限の確認は十分か。
- 秘密情報は適切な場所に保管されているか。
- 不要な機能を公開していないか。
- 外部ソフトウェアは適切に管理されているか。
- 想定外の操作や負荷に対応できるか。

こうした視点を持っていれば、AIに対して安全性を考慮した設計や見直しを求めることもできます。

もちろん、これだけでシステムの安全性を保証できるわけではありません。実際に公開する際には、適切な設計、検証、継続的な保守が必要です。

それでも、どこに問題が生まれ得るのかを知らなければ、何を確認すべきかも分かりません。

## 攻撃の名前よりも、攻撃が成立する理由を知る

新しい攻撃手法は、今後も生まれ続けるでしょう。

そのすべての名称や仕組みを覚え続けることは簡単ではありません。

しかし、システムが情報を受け取る場所、権限を判断する場所、秘密情報を管理する場所など、弱点が生まれる構造を理解していれば、初めて知る攻撃についても考えるための手がかりが得られます。

攻撃手法の名称を学ぶことは、その現象を理解し、知識を共有するために役立ちます。

ただし、名称を覚えること自体が学習の目的ではありません。

:::tip[今日のなるほど]
セキュリティホールとは、情報システムの機能や設計、設定などに存在する、悪用され得る安全性の弱点です。

攻撃手法は数多くありますが、弱点が生まれやすい場所や原因には共通する特徴があります。

**攻撃の名前を覚えることよりも、なぜそこに弱点が生まれ、なぜ攻撃が成立するのかを理解すること。**

それが、システムの安全性を考えるための土台になるのではないでしょうか。
:::
