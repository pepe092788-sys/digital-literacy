## 先頭の「00」が消えた日

ある日、社員番号の一覧を表計算ソフトで開いたら、こんなことが起きました。

| 元の社員番号 | 表示された値 |
| --- | --- |
| `001` | `1` |
| `002` | `2` |
| `010` | `10` |

「番号は同じなんだから、問題ないのでは？」と思うかもしれません。

でも、社員番号が `001` と決められているなら、`1` は別の表記です。ほかのシステムが `001` を探していると、`1` では一致しないことがあります。

なぜ、コンピュータは勝手にゼロを消してしまったのでしょう。

答えは、**そのデータを『計算する数字』として扱ったから**です。

## 数字に見えても、数字とは限らない

人間は「001」を見て、状況に応じて意味を判断します。

- りんごの個数なら、`001` 個も `1` 個も同じ量。
- 社員番号なら、`001` は人を識別するための記号。
- 郵便番号なら、先頭のゼロも住所を表す情報の一部。

コンピュータにも、この違いを伝える必要があります。

そこで登場するのが、**データ型**です。

データ型とは、簡単に言えば「このデータをどんな種類のものとして扱うか」という決まりです。型によって、できる操作や、値の表し方が変わります。

| データ型の例 | 値の例 | 主な用途 |
| --- | --- | --- |
| 整数（integer） | `1`, `42`, `-3` | 個数、回数など |
| 小数を扱う型 | `3.14`, `0.5` | 測定値など（用途によって型を選ぶ） |
| 文字列（string） | `"001"`, `"福井"` | 名前、識別番号、文章など |
| 真偽値（boolean） | `true`, `false` | はい／いいえ、条件の判定 |
| 日付・日時 | `2026-11-24` | 期限、予約日時など |

※型の名前や用意されている種類は、プログラミング言語やデータベースによって異なります。

## 「足し算」で違いが見えてくる

例えば、次の2つを比べてみましょう。

```python
1 + 2       # 3：数値の足し算
"1" + "2"   # "12"：文字列をつなげる
```

同じ「1」と「2」に見えても、数値として扱えば `3`、文字列として扱えば `"12"` になります。

文字列は、計算するための量ではなく、文字の並びです。だから `"001"` も、そのままの並びを保てます。

ここで大事なのは、**見た目だけではデータの意味は決まらない**ということ。

電話番号の `090...` や商品コードの `0007` も、数字だけで書かれていても、普通は足し算しません。こうした値は文字列として扱うのが自然です。

## 小数なのに、計算結果が少しずれる？

データ型の違いは、数字の計算にも現れます。

例えば、次の足し算です。

```python
0.1 + 0.2  # 0.30000000000000004
```

私たちが紙の上で計算すれば、答えは `0.3`。それなのに、プログラムでは末尾に小さな差が現れることがあります。

これは、コンピュータが計算を苦手としているからではありません。**小数を保存するときに、元の値をぴったり表せない場合がある**からです。

コンピュータが小数を扱う代表的な方法に、**浮動小数点数**があります。この方法では、保存できる情報量に限りがあり、`0.1` のような一部の小数は、厳密に同じ値ではなく、非常に近い値として記録されます。その値を使って計算すると、わずかな誤差が結果に現れることがあります。

もちろん、すべての小数で誤差が出るわけではありません。また、画面には `0.3` と表示されても、内部では近似値を扱っている場合があります。

測定値などでは、この小さな差が問題にならないこともあります。一方、金額のように正確な計算が必要な場合は、円単位の整数で管理したり、10進数を正確に扱える型を選んだりします。

ここで覚えておきたいのは、**「数値型なら、どんな数でも必ずぴったり保存できる」とは限らない**ということ。数値にも種類があり、目的に合った型を選ぶ必要があります。

なぜ特定の小数をぴったり表せないのか。その理由には、コンピュータが数を表す仕組みが関係しています。これは進数を学ぶときに、あらためて取り上げましょう。

## 日付は、ただの文字ではない

日付も面白い例です。

`2026-11-24` は、見た目だけなら文字列です。でも日付として扱えれば、次のようなことができます。

- 今日より前か後かを判定する。
- 期限まであと何日かを計算する。
- 1か月後の日付を求める。

ただし、日付には「月によって日数が違う」「時刻にはタイムゾーンがある」といったルールがあります。

だからこそ、日付を扱う専用の型や仕組みが役立ちます。

## 型を間違えると、何が起こる？

型の選び方を間違えると、次のような問題が起こります。

| データ | 間違った扱い方 | 起こり得る問題 |
| --- | --- | --- |
| 社員番号 `001` | 整数にする | 先頭のゼロが消える |
| 金額 | 近似的な小数で計算する | 丸め誤差が生じる |
| 日付 | ただの文字列として処理する | 日付の計算や妥当性確認が難しい |
| `true` / `false` の状態 | 曖昧な文字列で管理する | 表記ゆれで判定を間違える |

とはいえ、すべての値に唯一の正解の型があるわけではありません。用途やシステムの仕様に合わせて選びます。

## データベースでも、型が働いている

データベースに社員情報を保存するときも、項目ごとに型を決めることがあります。

| 項目 | 型の考え方 |
| --- | --- |
| 社員番号 | 文字列（先頭のゼロを保持する） |
| 氏名 | 文字列 |
| 入社日 | 日付 |
| 在籍中か | 真偽値、または状態を表す別の型 |
| 勤続年数 | 日付から計算することもできる |

こうしておくと、データを保存するときも、取り出して使うときも、意味に合った処理をしやすくなります。

なお、データベースによって型の種類や制約は異なります。また、**型を決めるだけでデータが必ず正しくなるわけではありません**。社員番号が重複していないか、日付が業務上妥当か、といった確認は別に必要です。

:::tip[今日のなるほど]
**コンピュータにとって大切なのは、データが何に見えるかではなく、何を意味するか。**

`001` を計算する数として扱えば `1` と同じ値。でも、人を識別する番号として扱えば、先頭のゼロにも意味があります。

データ型は、その意味に合った扱い方をコンピュータに伝えるための基本的な仕組みです。
:::

## おわりに ― 数字の顔をした、文字たち

社員番号、郵便番号、電話番号、商品コード。

私たちの周りには、数字で書かれているのに、計算するためではない情報がたくさんあります。

次に表計算ソフトやシステムでデータを扱うときは、少しだけ考えてみてください。

**「これは計算する数字だろうか。それとも、意味を持った記号だろうか？」**

その問いが、データを正しく扱う第一歩になります。
